# ADR-0001. Модульный монолит с локальными Tool

- **Дата:** 2026-11-14
- **Статус:** принято для первой версии

## Контекст и ограничения

Сервис выполняет две операции (`compare`, `forecast`), обе считают по данным из БД. Тяжёлых вычислений, GPU и отдельных релизов у Tool нет. Команда из 3–4 человек, число собственных сервисов не оценивается, а отдельный сетевой вызов добавляет таймауты, версии контрактов и частичные отказы (лекция 103). Единственная внешняя зависимость сети — футбольный API, и она идёт через адаптер (REQ-04).

## Решение

Одно приложение (Dispatcher, Registry, Tool, адаптер источника) и отдельная СУБД как второй контейнер. Tool выполняются в процессе приложения. Границы между модулями проходят по контрактам: Dispatcher знает только контракт Tool, Tool знает только `JobRepository`, `MatchRepository` и `SourcePort`.

## Альтернативы

- **Отдельный сервис для каждого Tool.** Независимая поставка и масштабирование, но для двух лёгких Tool они не нужны.
- **Каждый компонент своим сервисом** (Jobs, Dispatcher, Registry, History). Максимум независимости, но сетевая сложность и эксплуатация несоразмерны задаче.

## Цена решения

Общий релиз и общие ресурсы процесса. Независимость модулей держится на дисциплине: проверка импортов и отсутствие прямого доступа к чужим данным.

## Условия пересмотра

Появится тяжёлый или долгий Tool (например, в семестре с LLM); понадобится независимая поставка или масштабирование отдельного Tool; команда разделится на несколько команд с разными релизами. Пересмотр затронет один Tool, остальная система останется в общей поставке.
