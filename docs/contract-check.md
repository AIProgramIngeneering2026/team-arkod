# Проверка контракта API картами К1–К10

Контракт: [`api/openapi.yaml`](api/openapi.yaml).

## Проверка колодой

| Карта | Ответ контракта |
|---|---|
| К1. Двойной клик | `POST /jobs`: обязательный `Idempotency-Key`. Повтор с тем же ключом и тем же нормализованным телом возвращает ту же Job и тот же `id` (`202`); ключ с другим телом — `409 IDEMPOTENCY_KEY_REUSED`. См. `POST /jobs`, `IdempotencyKey`. |
| К2. Ответ потерялся | Клиент повторяет `POST /jobs` с тем же `Idempotency-Key`. Если первый запрос был зафиксирован, сервер возвращает ту же Job; если не был зафиксирован — создаёт одну Job. Связь ключа и Job хранится в PostgreSQL и переживает перезапуск. См. описание `POST /jobs`. |
| К3. Неизвестная операция | `operation` ограничена enum `compare_teams`, `predict_outcome`; неизвестное значение отклоняется с `422 VALIDATION_ERROR`, Job не создаётся. См. `CreateJobRequest.operation`, `ValidationError`. |
| К4. Кривые параметры | `CreateJobRequest` требует `operation` и `match_id`, запрещает дополнительные поля; `match_id` — положительное целое. Ошибка — `422` с `details[].field` и `details[].message`. См. `CreateJobRequest`, `ValidationError`. |
| К5. Воскрешение | Повторный запуск завершённой Job отдельной операцией API не предусмотрен. `POST /jobs` всегда создаёт новую логическую задачу при новом ключе; прежняя Job и её результат остаются неизменными. См. список `paths`; повтор с прежним ключом подчиняется К1. |
| К6. Отмена | `POST /jobs/{job_id}/cancel` отменяет `created`, `running`, `waiting_quota`. Для `running` применяется кооперативная отмена; частичный результат не публикуется. Успех — `200`, отмена `done` или `failed` — `409 JOB_NOT_CANCELLABLE`. См. `cancelJob`. |
| К7. Огромный вход | Тело запроса ограничено 64 KiB на HTTP-границе; превышение — `413 PAYLOAD_TOO_LARGE`, Job не создаётся. Для полей также действуют ограничения схемы. См. `PayloadTooLarge`, `CreateJobRequest`. |
| К8. Чужой или несуществующий id | Для чтения, результата и отмены проверяется владелец Job по проверенному Bearer-токену. Несуществующая и чужая Job не различаются во внешнем ответе: `404 NOT_FOUND`, чтобы не раскрывать наличие чужих идентификаторов. См. `bearerAuth`, `NotFound`. |
| К9. Перезапуск сервера | Job и ключ идемпотентности сохраняются в PostgreSQL. После аварийного перезапуска Job, оставшаяся в `running`, переводится в `failed` с `WORKER_INTERRUPTED`; автоматическое повторное выполнение не производится, чтобы не допустить скрытого повторного запуска. Клиент получает состояние через `GET /jobs/{job_id}`. См. схему `Job`, раздел «Что предложил ИИ» ниже. |
| К10. Внешний сервис | Тайм-ауты и временные 5xx ограниченно повторяются адаптером; `429` переводит Job в `waiting_quota`, затем она возвращается в `running` либо завершается `failed` по пределу ожидания. Некорректная структура ответа считается постоянной ошибкой Tool и завершает Job в `failed`. Для синхронного запроса списка при недоступности источника/кэша — `503 SERVICE_UNAVAILABLE`. См. `ServiceUnavailable`; состояния `JobStatus`. |

## Что предложил ИИ

### Промпт

> Выступи атакующим архитектором REST API. Проанализируй приложенный OpenAPI-контракт сервиса аналитики матчей АПЛ и колоду К1–К10. Найди минимум три конкретных сценария, на которые контракт не отвечает однозначно. Для каждого укажи входной запрос/событие, риск, ожидаемое поведение, HTTP-код и изменение контракта. Проверь идемпотентность, конкурентные запросы, права доступа, ограничения размера, перезапуск процесса и сбои football-data.org. Не предлагай неопределённые ответы вроде «обработать ошибку» — сформулируй проверяемое правило.

### Находка 1. Гонка двух одинаковых запросов на создание Job

**Сценарий:** два экземпляра backend одновременно получают `POST /jobs` с одним `Idempotency-Key` до того, как любой из них увидел запись ключа.

**Риск:** если проверка ключа и создание Job не атомарны, появятся две Job.

**Решение:** принято. В реализации ключ идемпотентности должен иметь уникальное ограничение в PostgreSQL в области владельца/клиента. Создание записи ключа и Job выполняется в одной транзакции. При конфликте уникальности backend читает существующую запись и сравнивает хеш нормализованного тела: одинаковый хеш — возвращает существующую Job; разный — `409 IDEMPOTENCY_KEY_REUSED`. Это уточнение добавлено в правила `POST /jobs`; требуется покрыть конкурентным интеграционным тестом.

### Находка 2. Доступ к Job другого пользователя

**Сценарий:** пользователь A угадывает или получает `job_id` пользователя B и вызывает `GET /jobs/{job_id}/result`.

**Риск:** утечка истории анализа и результатов.

**Решение:** принято. Добавлена Bearer-аутентификация; владелец определяется только по проверенному токену, а не по переданному клиентом ID. Для чужой и несуществующей Job возвращается одинаковый `404 NOT_FOUND`. Реализация должна проверять владельца во всех операциях с Job, включая отмену.

### Находка 3. Очень большой запрос

**Сценарий:** клиент отправляет тело размером в десятки мегабайт либо неизвестные дополнительные поля.

**Риск:** лишняя нагрузка на память и неоднозначное принятие параметров.

**Решение:** принято. Для тела запроса установлен предел 64 KiB; превышение возвращает `413 PAYLOAD_TOO_LARGE`. Схема создания Job использует `additionalProperties: false`, поэтому лишние поля отклоняются с `422 VALIDATION_ERROR`. Ограничение размера должно применяться на reverse proxy/HTTP-границе до разбора JSON.

### Находка 4. Перезапуск процесса во время выполнения

**Сценарий:** процесс завершился после перевода Job в `running`, но до сохранения результата.

**Риск:** Job навсегда останется `running` либо будет повторно выполнена без понятной клиенту семантики.

**Решение:** принято. При старте backend выполняет recovery-проверку: Job в `running`, не имеющие активного исполнителя, переводятся в `failed` с кодом `WORKER_INTERRUPTED`; результат не создаётся. Повторный запуск — новая Job с новым ключом. Это сознательно выбирает предсказуемость вместо автоматического повтора, который мог бы повторить внешние обращения. Проверка должна быть атомарной и покрыта интеграционным тестом.

## Принятые ограничения и открытые решения реализации

- Статистический алгоритм, минимальный размер выборки и версия метода должны быть зафиксированы отдельно до реализации прогнозного Tool. В ответе `PredictionResult.method` возвращается идентификатор версии фактически применённого метода.
- Источник расписания — football-data.org; API отдаёт нормализованные данные из локального кэша. Конкретные TTL кэша и максимальное время ожидания квоты задаются конфигурацией и должны быть согласованы с ADR.
- Bearer JWT — контрактное требование для изоляции Job. Способ выпуска и проверки токенов необходимо выбрать и задокументировать до реализации.
- Для отмены выполняется кооперативная остановка. Если используемый Tool нельзя прервать безопасно, реализация обязана проверить отмену перед публикацией результата и не переводить отменённую Job в `done`.
- `GET /matches` читает кэш расписания. Если кэш отсутствует и источник недоступен, API возвращает `503`; если кэш доступен, отдаёт его данные с `last_updated`.
