# Dispatcher

`arkod.application.dispatcher.Dispatcher` координирует выполнение Job в одном
backend-процессе. HTTP API вызывает `create`, `get`, `get_result` и `cancel`,
а фоновый поток приложения — `run`. Класс не содержит HTTP-маршрутов, SQL,
запросов к football-data.org и формул анализа.

Dispatcher не знает ни имён, ни классов конкретных Tool: он передаёт имя операции
в `Registry.get` и использует только общий контракт. Новый Tool добавляется
регистрацией без изменения Dispatcher.

## Ответственность

- `create` получает Tool через Registry, проверяет параметры его `params_model`
  и передаёт нормализованные параметры в атомарный `create_or_get` репозитория.
  Он возвращает сохранённую Job в `created`, не ожидая получения данных и расчёта.
- `execute` атомарно начинает готовую Job либо возобновляет `waiting_quota`.
  Затем вне транзакции получает снимок и вызывает `Tool.run(params, snapshot,
context)`. Переходы состояния проверяет доменная Job из PR №26.
- `ToolContext.is_cancelled` читает актуальное состояние через репозиторий.
  Сервис данных проверяет его перед обращениями к источнику; Dispatcher — перед
  вызовом Tool. Проверка состояния и сохранение итога проходят в одной транзакции,
  поэтому поздний ответ не переводит отменённую Job в `done` или `failed`.
- Успех сохраняется как полный `ToolResult`, включая `data` и `meta`.
  Ошибка сохраняется как код и сообщение Job. Некорректный ответ Tool и
  необработанное исключение дают `INTERNAL_ERROR` без технических подробностей
  в пользовательском сообщении.
- `SOURCE_RATE_LIMITED` от сервиса данных переводит Job в `waiting_quota`.
  В записи сохраняются время возобновления, начало ожидания и накопленное
  время ожидания. Без `retry_after_seconds` используется 60 секунд.
  Поток не засыпает на время квоты и может выполнять другие Job.
  При достижении суммарного предела ожидания Job завершается с
  `SOURCE_RATE_LIMITED`, даже если источник потребовал ждать дольше предела.
- Чтение, результат и отмена доступны владельцу. Чужая и отсутствующая Job
  дают `JobNotFound`. Повторная отмена `cancelled` возвращает текущую Job;
  отмена `done` или `failed` даёт `JobNotCancellable`.

## Сбой хранилища и отложенные переходы

Перед сохранением итога Dispatcher запоминает намерение перехода в памяти.
Если запись не удалась, следующий `run_once` повторяет её перед обработкой новых
задач. Повторный сбой сохраняет намерение для следующего прохода; сбой одной Job
не блокирует обработку остальных доступных записей.

- Если Tool уже вернул результат, повторяется только сохранение этого результата,
  включая `meta`. Tool и получение снимка повторно не вызываются.
- Если выполнение прервалось из-за `StorageError` до получения результата,
  после восстановления доступа Job завершается в `failed` с `SERVICE_UNAVAILABLE`.
- При неудачной записи `waiting_quota` повторяется тот же переход с исходными
  временем начала ожидания и временем возобновления. Ожидание не отсчитывается
  заново; предельное время учитывает и задержку сохранения.
- При подтверждённом откате захвата Job остаётся в `created` или `waiting_quota`
  и может быть взята обычным проходом. Если захват сохранился, но подтверждение
  потерялось, собственная прерванная попытка завершается с `SERVICE_UNAVAILABLE`.
- Если сохранение итога прошло, но подтверждение потерялось, повторная запись
  видит уже изменившееся состояние и отбрасывается. Конечные состояния неизменны.

При захвате в `JobRecord.execution_id` записывается новый маркер попытки.
Отложенный переход применяется только к `running` с тем же маркером, под общей
транзакционной блокировкой. Поэтому отмена имеет приоритет над поздним итогом,
а неудачный захват не позволяет завершить попытку другого исполнителя.

Прямой вызов `execute` передаёт `StorageError` вызывающему коду, сохранив намерение
перехода. Для его повторной записи нужен `run_once` или работающий цикл `run`.
`run_once` возвращает число уникальных Job, для которых обработана попытка
выполнения или отложенный переход.

Очередь принадлежит экземпляру Dispatcher и существует только в памяти.
При его замене готовые несохранённые результаты теряются; при запуске нового
Dispatcher используется существующий `recover` с `WORKER_INTERRUPTED` для
оставшихся `running`. После завершения процесса текущий репозиторий в памяти
теряет и сами задачи. Для восстановления состояния после завершения процесса
понадобится постоянное хранилище.

## Подключение

Зависимости задаются интерфейсами в `application/ports.py`: `JobRepository`,
`Registry`, `FootballDataService`. Реализация Registry — отдельная задача.
здесь оставлен только контракт `Registry.get(name) -> Tool`.
Для хранения реализован `infrastructure.memory_job_repository.MemoryJobRepository`.
Хранилище в памяти обеспечивает идемпотентность и атомарные изменения в пределах
процесса; после завершения процесса данные теряются. Сервис данных и конкретные
Tool подключает приложение. PostgreSQL для работы ядра не требуется.

Сборочный код backend должен передать реализации этих интерфейсов и управлять
потоком, например:

```python
from threading import Event, Thread

from arkod.application.dispatcher import Dispatcher
from arkod.infrastructure.memory_job_repository import MemoryJobRepository

# registry и data_service предоставляет приложение.
repository = MemoryJobRepository()
dispatcher = Dispatcher(repository, registry, data_service)
dispatcher.recover()  # До старта исполнителей, когда прежний процесс уже остановлен.
stop = Event()
worker = Thread(target=dispatcher.run, args=(stop,), daemon=True)
worker.start()

# При штатном завершении приложения:
stop.set()
worker.join()  # Даём текущему расчёту завершиться.
```

`run_once` выполняет один проход без ожидания; `execute(job_id)` — одну попытку.
Для тестов передаётся `clock`, поэтому проверка квот не требует реального ожидания.
`max_quota_wait_seconds` по умолчанию равен 300, интервал опроса `run` — 1 секунде.
Сетевые тайм-ауты и ограниченные повторы остаются обязанностью адаптера источника.

## Гарантии реализации хранилища

`JobRecord` содержит Job, владельца, `correlation_id`, расписание ожидания
и `execution_id` текущей попытки.
Все эти поля сохраняются вместе, включая полный успешный `ToolResult`.
Чтение возвращает отдельный снимок, а не общую изменяемую Job.

`create_or_get` атомарно создаёт Job и ключ идемпотентности в области владельца.
Повтор с теми же
операцией и нормализованными параметрами возвращает прежнюю Job; с другими
параметрами поднимает `IdempotencyConflict`. Новый ключ создаёт новую Job.

`transaction(job_id)` блокирует запись для всех исполнителей, выдаёт изменяемую
копию и сохраняет её целиком при успешном выходе. Исключение в теле откатывает
изменения. При сбое подтверждения записи её исход может быть неизвестен;
Dispatcher перечитывает состояние и маркер попытки перед повтором перехода.
Это обеспечивает атомарность захвата, отмены и публикации результата.
Транзакция не удерживается во время загрузки снимка или выполнения Tool.
Сбои хранилища поднимают `StorageError` и не маскируются под ошибки Tool.

`pending_ids` возвращает кандидатов в `created` и `waiting_quota`,
`running_ids` — задачи для восстановления. После чтения списка Dispatcher
повторно проверяет состояние под блокировкой. Постоянное хранение, реальные
блокировки БД и конкурентную идемпотентность нужно проверить интеграционно,
когда появится адаптер БД. Ему понадобятся транзакции, сохранение всех полей
JobRecord и уникальное ограничение по `(owner_id, idempotency_key)`.

## Проверка

```text
uv sync --locked
uv run pytest -q
uv build --wheel
```

Тесты покрывают параметры и идемпотентность, доступ владельца, передачу снимка,
ошибки, квоту и восстановление расписания, отмену с поздним ответом, конкурентный
запуск одной Job двумя экземплярами Dispatcher и добавление нового Tool только
через регистрацию. Используется рабочий репозиторий в памяти; Registry, вычисления
и источник данных заменены тестовыми заглушками. Поведение реализации Registry
здесь не проверяется. Существующие тесты Job сохранены.
Дополнительно проверяются повторная запись результата без повторного расчёта,
отмена отложенного перехода, серия сбоев записи, сохранение расписания квоты,
откат захвата, потеря подтверждения записи и защита попытки другого исполнителя.
